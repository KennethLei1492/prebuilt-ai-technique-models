# Task Decomposition Model

_Used by: task_decomposition_model/._  Dossier: `docs/research/task-decomposition.json` (final). Back to the [index](../RESEARCH_BIBLIOGRAPHY.md).

## Summary

Task decomposition is the family of techniques by which an LLM-based system turns a natural-language task into an explicit structure of smaller sub-problems (a sequence, a tree, or a dependency DAG), solves them with the appropriate executor (an LLM prompt, a tool, a retriever, a symbolic function, or a sub-agent), and composes the partial results into a final answer. The field grew out of chain-of-thought prompting (Wei et al., NeurIPS 2022: PaLM-540B GSM8K 17.9% -> 56.9%) and matured along three axes. (1) Prompting-based decomposition: Least-to-Most (SCAN length split 16.2% -> 99.7%; GSM8K 5+-step problems 39.1% -> 45.2%), Decomposed Prompting (modular sub-task handler library with recursive and symbolic handlers; MultiArith 78 -> 95, GSM8K 36 -> 50.6 with a decomposed answer-extraction step), Successive Prompting (+~5 F1 on few-shot DROP), Self-Ask (compositionality gap ~40% independent of scale; Bamboogle 46.4 -> 57.6 -> 60.0 with search), and Plan-and-Solve (zero-shot PS+ 76.7 avg vs 70.4 Zero-shot-CoT, missing-step errors 12% -> 7%). (2) Search-based reasoning that treats decomposition as exploration: Tree of Thoughts (Game of 24 4% -> 74% with BFS b=5), Graph of Thoughts (arbitrary graph with Aggregate/Refine; sorting 128 elements ~62% lower error and >31% lower cost than ToT), and RAP (LLM as world model inside MCTS; Blocksworld 4-step 0.02 -> 0.88 with LLaMA-33B). (3) Agentic planner-executor systems: ReAct interleaves thought/action/observation (ALFWorld 71% best-of-6, WebShop 40% success); ReWOO decouples a blueprint of #E placeholders from tool execution (HotpotQA tokens 9795 -> 1986, ~5x); LLMCompiler emits a DAG with $N placeholders and schedules independent calls in parallel (up to 3.7x latency, 6.7x cost reduction vs ReAct, ~9% accuracy gain); HuggingGPT encodes tasks as JSON with id/dep/args fields; ADaPT decomposes recursively only on executor failure (ALFWorld 43.3 -> 71.6, WebShop 32 -> 44, TextCraft 19 -> 52 vs ReAct, d_max=3-4); TDAG re-decomposes after each sub-result and generates sub-agents (cascading failures 34.8% for Plan-and-Execute vs 4.35%).

The literature also establishes the hard limits that a production component must design around. Reflexion (HumanEval 80.1 -> 91.0 pass@1; AlfWorld +22% absolute over 12 trials) and Self-Refine (~20% absolute average gain) show that verbal reflection and replanning help, but Huang et al. (ICLR 2024) show these gains vanish without external feedback (GPT-4 GSM8K 95.5 -> 91.5 -> 89.0 under intrinsic self-correction; GPT-3.5 CommonSenseQA 75.8 -> 38.1). Valmeekam et al. (NeurIPS 2023 spotlight) show GPT-4 produces valid Blocksworld plans only ~34% of the time autonomously (~12% averaged across domains), but 82% of failed instances are fixed by a sound verifier (VAL) within ~3.7 backprompt rounds, and Faith and Fate shows that compositional accuracy decays with computation-graph depth because models do linearized subgraph matching. AgentBench finds that the dominant agent failure is Task Limit Exceeded (looping), followed by Invalid Format and Invalid Action. The state of practice (Anthropic's "Building effective agents", LangChain's planning-agents write-up, Anthropic prompting docs) converges on: use the simplest structure that works (prompt chaining -> routing -> parallel sectioning/voting -> orchestrator-workers -> evaluator-optimizer -> autonomous agent), make planning steps visible and loggable, encode dependencies explicitly so independent work runs in parallel, cap iterations, and verify with external signals rather than self-judgment.

1. **Jason Wei, Xuezhi Wang, Dale Schuurmans, Maarten Bosma, Brian Ichter, Fei Xia, Ed Chi, Quoc Le, Denny Zhou (2022).** *Chain-of-Thought Prompting Elicits Reasoning in Large Language Models.* NeurIPS 2022 (Main Conference Track); arXiv 2201.11903. arXiv:2201.11903  
   <https://arxiv.org/abs/2201.11903>  _(verified)_
   - Why it is highly rated: Roughly 6,000 citations per a third-party aggregator seen in search results; Paper Digest ranks it the No. 2 most influential NeurIPS 2022 paper. Foundational classic the whole decomposition literature builds on.
   - Key contribution: Prompting with exemplars containing intermediate natural-language reasoning steps raises PaLM-540B GSM8K accuracy from 17.9% (standard) to 56.9% (58.6% with an external calculator), surpassing finetuned GPT-3 with a verifier (55%); SVAMP 69.4 -> 79.0, MAWPS 79.2 -> 93.3, AQuA 25.2 -> 35.8. Ablations on LaMDA-137B (standard 6.5%, CoT 14.3%, equation-only 5.4%, variable-compute 6.4%, reasoning-after-answer 6.1%) show the natural-language intermediate steps themselves carry the gain. CoT is emergent: it does not help below ~100B parameters and smaller models produce fluent but illogical chains.
   - Design implication: Every decomposition component should request explicit intermediate reasoning before committing to sub-goals or answers, and should allocate output room for it. Because CoT quality is model-size dependent, the planner role should be assigned to the strongest available model while executors can be smaller. Reasoning must precede the answer in the output format; verifying the answer-first variant is useless.
   - Verification evidence: arXiv 2201.11903: title match 1.00, year 2022

2. **Xuezhi Wang, Jason Wei, Dale Schuurmans, Quoc Le, Ed Chi, Sharan Narang, Aakanksha Chowdhery, Denny Zhou (2022).** *Self-Consistency Improves Chain of Thought Reasoning in Language Models.* ICLR 2023; arXiv 2203.11171. arXiv:2203.11171  
   <https://arxiv.org/abs/2203.11171>  _(verified)_
   - Why it is highly rated: ICLR 2023 top-venue paper; the standard multi-plan selection baseline used by ToT, RAP, ReAct and Huang et al. Widely adopted in production as majority voting.
   - Key contribution: Replace greedy decoding with sampling 40 diverse reasoning paths (T=0.7, top-k=40 for PaLM-540B; T=0.5, top-k=40 for LaMDA/UL2) and majority-vote the final answer. PaLM-540B GSM8K 56.5% -> 74.4% (+17.9), SVAMP +11.0, AQuA +12.2, StrategyQA +6.4, ARC-challenge +3.9. Accuracy rises monotonically with path count and saturates quickly (UL2-20B AQuA: 5 paths 24.9, 10 -> 25.3, 20 -> 26.7, 40 -> 26.9).
   - Design implication: Use sampled-plan voting as the cheapest form of plan selection: generate k candidate decompositions or sub-answers at T~0.7 and pick the modal one. Since gains saturate, default k=5-10 for latency-sensitive paths and k=20-40 only for high-stakes final answers. Huang et al. later show plain self-consistency beats multi-agent debate at equal sample counts, so prefer it over more elaborate critique loops when no external signal is available.
   - Verification evidence: arXiv 2203.11171: title match 1.00, year 2022

3. **Denny Zhou, Nathanael Schärli, Le Hou, Jason Wei, Nathan Scales, Xuezhi Wang, Dale Schuurmans, Claire Cui, Olivier Bousquet, Quoc Le, Ed Chi (2022).** *Least-to-Most Prompting Enables Complex Reasoning in Large Language Models.* ICLR 2023; arXiv 2205.10625. arXiv:2205.10625  
   <https://arxiv.org/abs/2205.10625>  _(verified)_
   - Why it is highly rated: ICLR 2023; OpenAlex lists 316 citations (OpenAlex undercounts arXiv-first work). The canonical decomposition-first prompting method.
   - Key contribution: Two stages: (1) a decomposition prompt returns an ordered list of simpler subquestions; (2) each subquestion is solved sequentially with all prior subquestions and generated answers appended, with the original problem as the final subquestion. code-davinci-002 with 14 exemplars: SCAN length split 99.7% vs 16.2% CoT (rivaling neuro-symbolic models trained on >15k examples); last-letter concatenation at length 12: 74.0 vs 31.8 CoT; GSM8K overall 62.39 vs 60.87 but on 5+-step problems 45.23 vs 39.07; DROP non-football 82.45 vs 74.77.
   - Design implication: Decomposition pays off specifically on easy-to-hard generalization and long-horizon problems (5+ steps), and is roughly neutral on 2-step problems, so a production planner should gate decomposition by estimated depth rather than always decomposing. Implement sub-goal solving as a running context in which each solved sub-goal's answer is appended before the next, and always re-ask the original question last to force composition.
   - Verification evidence: arXiv 2205.10625: title match 1.00, year 2022

4. **Tushar Khot, Harsh Trivedi, Matthew Finlayson, Yao Fu, Kyle Richardson, Peter Clark, Ashish Sabharwal (2022).** *Decomposed Prompting: A Modular Approach for Solving Complex Tasks.* ICLR 2023 (camera ready); arXiv 2210.02406. arXiv:2210.02406  
   <https://arxiv.org/abs/2210.02406>  _(verified)_
   - Why it is highly rated: ICLR 2023 top-venue paper from AI2; directly spawned ADaPT and is the reference design for modular sub-task handler libraries.
   - Key contribution: A decomposer LLM writes a program of sub-task calls; each sub-task is served by a handler from a shared library that can be a few-shot prompt, a further-decomposed prompt (recursion), or a symbolic function (e.g., Elasticsearch retrieval). Recursive list reversal splits lists in half until a base case (<4 items) that CoT handles accurately and generalizes to 10-item lists where CoT fails; k-th letter concatenation stays near 100% on longer inputs while CoT drops; CommaQA-E compositional split improves while CoT drops; open-domain multi-hop QA (2WikiMultihopQA, MuSiQue, HotpotQA) with Flan-T5-XXL beats all baselines; a decomposed answer-extraction sub-task lifts MultiArith 78 -> 95 and GSM8K 36 -> 50.6.
   - Design implication: Model the component as a registry of sub-task handlers (LLM prompt, tool, retriever, recursive planner) addressed by name, so handlers can be unit-tested, swapped, and reused across domains without touching the decomposer. Make recursion a first-class handler type with an explicit base-case predicate (input size or confidence). Dedicated answer-extraction/format-normalization sub-tasks are cheap and measurably improve downstream parsing.
   - Verification evidence: arXiv 2210.02406: title match 1.00, year 2022

5. **Dheeru Dua, Shivanshu Gupta, Sameer Singh, Matt Gardner (2022).** *Successive Prompting for Decomposing Complex Questions.* EMNLP 2022 (main, 2022.emnlp-main.81); arXiv 2212.04092. arXiv:2212.04092  
   <https://arxiv.org/abs/2212.04092>  _(verified)_
   - Why it is highly rated: EMNLP 2022 main-conference paper; cited as a baseline by Decomposed Prompting and later decomposition work.
   - Key contribution: Iteratively alternates a question-decomposition step (produce the next simple sub-question) and an answering step until the final answer, separating the supervision for decomposing from the supervision for answering. This allows in-context exemplar selection per reasoning step, synthetic generation of intermediate-question training data, and swapping in fine-tuned components for steps an LLM handles poorly. Best model gains ~5% absolute F1 on few-shot DROP versus a state-of-the-art model with equal supervision.
   - Design implication: Interleaving 'next sub-question' and 'answer it' as separate calls lets the component retrieve different few-shot exemplars for each step and route individual steps to specialized/fine-tuned executors (e.g., a numeric-extraction model for test logs). Keep decomposition data (sub-question traces) as a reusable asset: it can bootstrap a smaller planner, which ReWOO later confirms (7B planner matching GPT-3.5 blueprints).
   - Verification evidence: arXiv 2212.04092: title match 1.00, year 2022

6. **Ofir Press, Muru Zhang, Sewon Min, Ludwig Schmidt, Noah A. Smith, Mike Lewis (2022).** *Measuring and Narrowing the Compositionality Gap in Language Models (Self-Ask).* Findings of EMNLP 2023; arXiv 2210.03350. arXiv:2210.03350  
   <https://arxiv.org/abs/2210.03350>  _(verified)_
   - Why it is highly rated: Findings of EMNLP 2023; the 'compositionality gap' metric and self-ask + search pattern are widely reused in retrieval-augmented decomposition.
   - Key contribution: Defines the compositionality gap as the fraction of multi-hop questions whose sub-questions are all answered correctly but whose composition fails; it stays roughly constant at ~40% across GPT-3 sizes, so scale alone does not fix composition. Self-ask makes the model explicitly pose and answer follow-up questions before the final answer and lets a search engine answer each follow-up. Davinci-002 accuracy: Bamboogle direct 17.6 / CoT 46.4 / self-ask 57.6 / self-ask+search 60.0; 2WikiMultiHopQA 25.4 / 29.8 / 30.0 / 40.1; Musique 5.6 / 12.6 / 13.8 / 15.2.
   - Design implication: Track the compositionality gap as a first-class metric: sub-goal correctness vs end-to-end correctness. Structure sub-question output as a parseable scaffold ('Follow up:' / 'Intermediate answer:') so a retrieval tool can be injected at each hop; the biggest gains come when retrieval is attached to decomposed sub-questions (2Wiki +10 points) rather than to the original question.
   - Verification evidence: arXiv 2210.03350: title match 0.94, year 2022

7. **Lei Wang, Wanyu Xu, Yihuai Lan, Zhiqiang Hu, Yunshi Lan, Roy Ka-Wei Lee, Ee-Peng Lim (2023).** *Plan-and-Solve Prompting: Improving Zero-Shot Chain-of-Thought Reasoning by Large Language Models.* ACL 2023 (long, pp. 2609-2634); arXiv 2305.04091. arXiv:2305.04091  
   <https://arxiv.org/abs/2305.04091>  _(verified)_
   - Why it is highly rated: ACL 2023 main-conference long paper; the zero-shot plan-then-execute prompt is reproduced in many production prompt libraries and surveys.
   - Key contribution: Zero-shot trigger that first devises a plan then executes it. PS: 'Let's first understand the problem and devise a plan to solve the problem. Then, let's carry out the plan and solve the problem step by step.' PS+ adds variable extraction and calculation-care instructions. text-davinci-003 averages over six arithmetic sets: Zero-shot-CoT 70.4, PS 72.9, PS+ 76.7, Zero-shot-PoT 73.5, few-shot Manual-CoT 77.6 (GSM8K: 56.4 -> 59.3). Error analysis on 100 wrong GSM8K answers: missing-step errors drop 12% -> 7% and calculation errors 7% -> 5%, while semantic misunderstanding stays at 27%.
   - Design implication: A cheap, model-agnostic default for the 'plan' phase: a single call that must emit the plan before executing it, with domain-specific 'extract relevant variables' instructions (e.g., extract part numbers, tolerances, log timestamps). Expect it to fix omitted steps but not semantic misreadings; semantic errors require retrieval/grounding or verification, not more planning text.
   - Verification evidence: arXiv 2305.04091: title match 1.00, year 2023

8. **Shunyu Yao, Jeffrey Zhao, Dian Yu, Nan Du, Izhak Shafran, Karthik Narasimhan, Yuan Cao (2022).** *ReAct: Synergizing Reasoning and Acting in Language Models.* ICLR 2023; arXiv 2210.03629. arXiv:2210.03629  
   <https://arxiv.org/abs/2210.03629>  _(verified)_
   - Why it is highly rated: ICLR 2023; the default agent loop in LangChain, LlamaIndex and most agent frameworks; the baseline every planner-executor paper (ReWOO, LLMCompiler, ADaPT, Reflexion) compares against.
   - Key contribution: Interleaves Thought / Action / Observation steps. PaLM-540B: HotpotQA EM standard 28.7, CoT 29.4, CoT-SC 33.4, ReAct 27.4, ReAct->CoT-SC 35.1, CoT-SC->ReAct 34.2; FEVER 57.1 / 56.3 / 60.4 / 60.9 / 62.0 / 64.6. ALFWorld success 71% (best of 6; 57% average) vs Act 45% and BUTLER 37% (+34% absolute); WebShop 40.0% success / 66.6 score vs IL+RL 28.7% (+10% absolute). Error analysis on HotpotQA: ReAct hallucination 0% vs CoT 56%, but reasoning errors 47% vs 16% and search-result errors 23%.
   - Design implication: Interleaved act-observe loops are the right executor for sub-goals that need environment feedback, and they nearly eliminate hallucination by grounding on observations. But they are less flexible in reasoning and more prone to loops, so production executors need a step cap, a repeated-action detector, and a fallback to pure reasoning (ReAct->CoT-SC) when the loop stalls. Combining both modes beats either alone.
   - Verification evidence: arXiv 2210.03629: title match 1.00, year 2022

9. **Shunyu Yao, Dian Yu, Jeffrey Zhao, Izhak Shafran, Thomas L. Griffiths, Yuan Cao, Karthik Narasimhan (2023).** *Tree of Thoughts: Deliberate Problem Solving with Large Language Models.* NeurIPS 2023; arXiv 2305.10601. arXiv:2305.10601  
   <https://arxiv.org/abs/2305.10601>  _(verified)_
   - Why it is highly rated: NeurIPS 2023; OpenAlex lists 565 citations (undercount for arXiv-first work); the reference search-based reasoning method generalized by GoT and RAP.
   - Key contribution: Frames problem solving as search over 'thoughts' (coherent intermediate steps) with LLM-based state evaluation (value scoring sure/maybe/impossible, or voting) and BFS/DFS with pruning and backtracking. Game of 24: IO 7.3%, CoT 4.0%, CoT-SC(k=100) 9.0%, ToT b=1 45%, ToT b=5 74%; cost per case $0.74 (5.5k generated tokens) vs CoT best-of-100 $0.47. Creative writing GPT-4 coherency 7.56 vs CoT 6.93 (depth 2, b=1, 5 plans voted 5 times). Mini crosswords word-level 60% vs 15.6%; ablations: no pruning 41.5%, no backtracking 20%.
   - Design implication: Use search only where sub-goals are verifiable or scorable and the task has a tree structure; it costs several times CoT in tokens. Default BFS with breadth b=5 and value-voting with 3-5 samples per state; include pruning (drop 'impossible') and backtracking, which the ablations show are the components that matter. Expose breadth, depth, and a step cap (ToT used 100 DFS steps / 10 intermediate steps) as configuration.
   - Verification evidence: arXiv 2305.10601: title match 1.00, year 2023

10. **Maciej Besta, Nils Blach, Ales Kubicek, Robert Gerstenberger, Michal Podstawski, Lukas Gianinazzi, Joanna Gajda, Tomasz Lehmann, Hubert Niewiadomski, Piotr Nyczyk, Torsten Hoefler (2023).** *Graph of Thoughts: Solving Elaborate Problems with Large Language Models.* AAAI 2024; arXiv 2308.09687. arXiv:2308.09687  
   <https://arxiv.org/abs/2308.09687>  _(verified)_
   - Why it is highly rated: AAAI 2024 (top-tier AI venue); from ETH Zurich SPCL with an open-source framework; introduces the latency/volume analysis used to compare prompting topologies.
   - Key contribution: Models LLM thoughts as vertices and dependencies as edges in an arbitrary graph, adding operations CoT/ToT lack: Aggregate (merge many thoughts), Refine (self-loop improvement), Generate(k), Score, KeepBest(h). Introduces 'volume' (number of thoughts that can influence a thought): CoT latency N / volume N; ToT latency log_k N / volume O(log_k N); GoT latency log_k N / volume N. Sorting 128 elements with GPT-3.5: ~62% lower median error and >31% lower cost than ToT; ~65% lower error than CoT at 64 elements; set intersection, keyword counting and document merging (NDA merge) handled with split-solve-merge graphs.
   - Design implication: The decomposition engine should represent a plan as a general DAG supporting map (split), reduce (aggregate), and refine (loop) nodes rather than a tree, because divide-and-conquer with merge is what makes long inputs (large specs, log files, BOMs) tractable. GoT's sorting recipe (split into 2, sort each 5x keep best 3, merge 10x keep best, improve 10x keep best) is a reusable template for merge-heavy engineering documents.
   - Verification evidence: arXiv 2308.09687: title match 1.00, year 2023

11. **Shibo Hao, Yi Gu, Haodi Ma, Joshua Jiahua Hong, Zhen Wang, Daisy Zhe Wang, Zhiting Hu (2023).** *Reasoning with Language Model is Planning with World Model (RAP).* EMNLP 2023; arXiv 2305.14992. arXiv:2305.14992  
   <https://arxiv.org/abs/2305.14992>  _(verified)_
   - Why it is highly rated: EMNLP 2023 main conference; released the LLM Reasoners library; one of the two main MCTS-over-LLM references in the planning survey (with LLM-MCTS).
   - Key contribution: Uses the same LLM as reasoning agent (proposes actions) and world model (predicts next state) inside MCTS (UCT selection, expansion, simulation, backpropagation). Rewards: action log-likelihood, state confidence (modal answer share across samples), self-evaluation P('Yes'), and task heuristics (goal conditions met). Blocksworld success (LLaMA-33B): CoT 0.17/0.02/0.00 at 2/4/6 steps vs RAP(20) 1.00/0.88/0.42, beating GPT-4 CoT (0.50/0.63/0.40), a 33% relative gain. GSM8K: CoT 29.4, CoT+SC(10) 46.8, L2M 25.5, RAP(10) 48.6, RAP(10)+aggregation 51.6. PrOntoQA proof accuracy 64.8 -> 78.8.
   - Design implication: For plan generation where the system can simulate state transitions (configuration changes, test-sequence planning, CAD assembly ordering), MCTS with 10-20 iterations and a blended reward (model confidence + task heuristic) materially outperforms sequential prompting. Task-specific heuristics (e.g., number of requirements satisfied, tests passing) should be pluggable reward functions.
   - Verification evidence: arXiv 2305.14992: title match 0.97, year 2023

12. **Binfeng Xu, Zhiyuan Peng, Bowen Lei, Subhabrata Mukherjee, Yuchen Liu, Dongkuan Xu (2023).** *ReWOO: Decoupling Reasoning from Observations for Efficient Augmented Language Models.* arXiv preprint 2305.18323 (no peer-reviewed venue listed). arXiv:2305.18323  
   <https://arxiv.org/abs/2305.18323>  _(verified)_
   - Why it is highly rated: Widely adopted in industry: implemented as a reference planner in LangGraph's planning-agents guide alongside Plan-and-Execute and LLMCompiler.
   - Key contribution: Splits the augmented LM into Planner (writes a full blueprint of (Plan, #E_s) pairs with evidence variables before any tool runs), Worker (executes tools and fills #E variables), and Solver (composes final answer). gpt-3.5-turbo: HotpotQA accuracy 40.8 -> 42.4 with tokens 9795 -> 1986 (~5x); TriviaQA 59.4 -> 66.6 with tokens 4213 -> 1341; average 64% token reduction across six benchmarks with reported average +4.4% accuracy. With all tools returning 'No evidence found', accuracy drops 29.2 vs ReAct's 40.8 and tokens fall rather than rise. A LoRA-tuned 7B LLaMA planner trained on GPT-3.5 blueprints matches GPT-3.5 on HotpotQA/TriviaQA/StrategyQA.
   - Design implication: Plan-once-execute-many is the default for cost: each tool call no longer re-sends the full history. Use typed evidence variables (#E1...) that later steps reference, which also enables static dependency analysis. Because the planner never sees observations, add a replanning hook for tool failures. Blueprints are an ideal distillation target: log them to fine-tune a small planner.
   - Verification evidence: arXiv 2305.18323: title match 1.00, year 2023

13. **Sehoon Kim, Suhong Moon, Ryan Tabrizi, Nicholas Lee, Michael W. Mahoney, Kurt Keutzer, Amir Gholami (2023).** *An LLM Compiler for Parallel Function Calling.* ICML 2024; arXiv 2312.04511. arXiv:2312.04511  
   <https://arxiv.org/abs/2312.04511>  _(verified)_
   - Why it is highly rated: ICML 2024; Semantic Scholar lists 242 citations; implemented in LangGraph and referenced by OpenAI/LangChain as the parallel planning pattern.
   - Key contribution: Three components: a Planner that streams a DAG of tasks whose arguments reference earlier outputs with $N placeholders; a Task Fetching Unit that resolves dependencies greedily and dispatches tasks the moment inputs are available (no LLM needed); an Executor that runs tools concurrently; plus dynamic replanning via a joiner that feeds results back to the planner. Versus ReAct: HotpotQA GPT-3.5 1.80x latency / 3.37x cost at equal accuracy (62.0 vs 62.5); Movie Recommendation 3.74x latency / 6.73x cost with accuracy 77.1 vs 72.5; ParallelQA GPT-4 2.15x / 4.65x; Game of 24 vs ToT 2.89x faster at 75.3 vs 74.0. Up to 35% lower latency than OpenAI parallel function calling. Documents ReAct failure modes: ~10% of LLaMA-2 HotpotQA runs looped past 4 calls; ~85% of GPT-3.5 Movie Rec runs stopped before completing all 8 searches.
   - Design implication: The production planner should emit a machine-readable DAG with explicit placeholder references, and a non-LLM scheduler should run ready nodes concurrently (topological frontier scheduling). Keep a joiner/replan step bounded by a max replan count. This is the single highest-leverage design for latency and cost in tool-heavy engineering workloads (e.g., querying many test-log shards or requirement IDs in parallel).
   - Verification evidence: arXiv 2312.04511: title match 1.00, year 2023

14. **Yongliang Shen, Kaitao Song, Xu Tan, Dongsheng Li, Weiming Lu, Yueting Zhuang (2023).** *HuggingGPT: Solving AI Tasks with ChatGPT and its Friends in Hugging Face.* NeurIPS 2023 (Main Conference Track); arXiv 2303.17580. arXiv:2303.17580  
   <https://arxiv.org/abs/2303.17580>  _(verified)_
   - Why it is highly rated: NeurIPS 2023; Paper Digest lists it among the most influential NeurIPS 2023 papers; the JARVIS open-source release had broad industry uptake.
   - Key contribution: Four-stage controller: task planning, model selection, execution, response generation. Plans are JSON task lists with fields task, id, dep (prerequisite ids, [-1] if none) and args (text/image/audio/video), using '<resource>-task_id' placeholders substituted at run time; tasks run when all deps finish and independent tasks run in parallel. Uses specification-based instruction (fixed template slot filling), demonstration-based parsing (few-shot), temperature 0 and a logit bias of 0.2 on '{' and '}' to enforce JSON. Planning evaluation on 3,497 GPT-4-labeled requests: GPT-3.5 single-task F1 54.45, sequential F1 51.92, graph F1 51.91; on a 46-example human set GPT-4 reaches 41.4% (sequential) and 58.3% (graph) vs GPT-3.5 18.2% / 20.8%. Limitations: planning quality not guaranteed, multiple-call latency, context limits on tool descriptions, format instability.
   - Design implication: Adopt a strict JSON task schema (id, type, deps, args with typed resource references) validated by a parser, with constrained decoding or a repair step, because planning F1 is only ~50% and format instability causes workflow failures. Model-selection by capability description is the general pattern for routing sub-tasks to specialized engineering tools (static analyzers, CAD parsers, log analyzers). Budget the planner's context for tool descriptions and retrieve only relevant tools when the catalog is large.
   - Verification evidence: arXiv 2303.17580: title match 1.00, year 2023

15. **Archiki Prasad, Alexander Koller, Mareike Hartmann, Peter Clark, Ashish Sabharwal, Mohit Bansal, Tushar Khot (2023).** *ADaPT: As-Needed Decomposition and Planning with Language Models.* Findings of NAACL 2024; arXiv 2311.05772. arXiv:2311.05772  
   <https://arxiv.org/abs/2311.05772>  _(verified)_
   - Why it is highly rated: Findings of NAACL 2024 from UNC/AI2 (authors of Decomposed Prompting); the main reference for recursive, failure-triggered decomposition and used as a baseline by TDAG.
   - Key contribution: A recursive controller first lets a ReAct-style executor attempt the whole task; only on self-reported failure does it call a planner that emits 3-5 sub-tasks joined by And (sequential) / Or (alternatives) operators, each recursively passed back to the controller until success or depth d_max (3 for ALFWorld/WebShop, 4 for TextCraft). GPT-3.5-class models: ALFWorld 71.6 vs ReAct 43.3, Plan-and-Execute 43.3, Reflexion 57.5; WebShop 44.0 vs 32.0 / 17.0 / 35.0; TextCraft 52.0 vs 19.0 / 27.0 / 32.0. ## Implementable techniques

- **Decomposition-first sequential solving with answer carry-forward (Least-to-Most / Plan-and-Solve)** - Stage 1 (decompose): prompt the planner with the task plus domain exemplars and require an ordered list of sub-questions whose last item is the original task. Stage 2 (solve): for i in 1..n, build a prompt containing the task context, all prior (sub-question, answer) pairs, and sub-question i; store the answer. Return the answer to the final (original) sub-question. Zero-shot variant: a single call with the PS+ trigger ('first understand the problem, extract relevant variables and their corresponding numerals, and make a plan; then carry out the plan, calculate intermediate variables, solve step by step, and show the answer'). Add an answer-extraction sub-task at the end that normalizes the final output to the required schema.
  - When to use: Tasks with predictable sub-steps, long horizons (5+ reasoning steps) or easy-to-hard generalization (longer inputs than exemplars); document- or spec-analysis tasks where sub-questions can be enumerated up front.
  - Trade-offs: n+1 LLM calls instead of 1; roughly neutral on 2-3 step problems (GSM8K 2-step 76.7 vs 74.5) and strongly positive on 5+ steps (39.1 -> 45.2) and length generalization (SCAN 16% -> 99.7%). Fixed plans are brittle to early errors (decomposition-first con in the planning survey). Fixes missing-step errors (12% -> 7%) but not semantic misunderstanding (27%).
  - Literature defaults: Decompose only when estimated depth >= 3 steps or input length exceeds exemplar length; 3-8 sub-questions per plan (ADaPT uses 3-5); temperature 0 for decomposition; carry all prior sub-answers forward (L2M); always append the original question as the last sub-question; add a dedicated answer-extraction step (DecomP: MultiArith 78 -> 95).
  - Sources: Least-to-Most Prompting Enables Complex Reasoning in Large Language Models; Plan-and-Solve Prompting: Improving Zero-Shot Chain-of-Thought Reasoning by Large Language Models; Decomposed Prompting: A Modular Approach for Solving Complex Tasks

- **Modular sub-task handler library with recursive and symbolic handlers (Decomposed Prompting)** - Maintain a registry H = {name -> handler} where a handler is one of: (a) a few-shot LLM prompt specialized to one sub-task, (b) a symbolic function (retriever query, calculator, regex extractor, test runner, CAD/BOM parser), (c) the decomposer itself (recursion). The decomposer LLM emits a program: a sequence of (handler_name, input_expression) steps where inputs may reference earlier outputs by variable. The controller executes steps, dispatching to handlers; recursive handlers split the input (e.g., halve a list, chunk a document) until a base-case predicate (size < threshold or confidence > tau) holds, then merge. Each handler has its own exemplars, tests and version.
  - When to use: Multi-domain deployments where sub-tasks recur (extract IDs, look up a standard clause, compute a tolerance stack-up); long inputs that exceed what one call handles reliably (large specs, log files, BOMs); when parts of the task are better done symbolically.
  - Trade-offs: Upfront engineering to build and test handlers; the decomposer must know the handler catalog (context cost, mitigated by retrieving relevant handlers). Large gains in length generalization and compositional splits; symbolic handlers eliminate hallucination for their step. Recursion needs a hard depth cap.
  - Literature defaults: Base case for recursion at inputs small enough for a single-call accuracy >= ~95% on a validation set (DecomP used list length < 4); max recursion depth 3-4 (ADaPT d_max); handler descriptions written as docstrings with examples and edge cases (Anthropic ACI guidance); retrieve top-k handlers (k ~ 5-10) into the planner prompt when the catalog exceeds ~20 entries (HuggingGPT context limitation).
  - Sources: Decomposed Prompting: A Modular Approach for Solving Complex Tasks; Successive Prompting for Decomposing Complex Questions; Graph of Thoughts: Solving Elaborate Problems with Large Language Models

- **DAG planning with placeholder references and topological frontier scheduling (LLMCompiler / ReWOO / HuggingGPT)** - Planner emits a plan as a list of nodes {id, tool_or_handler, args, deps} where args may contain placeholders ($k or #E_k or <resource>-k) referring to outputs of node k; deps is derived from placeholders (plus explicit deps). Validate: all referenced ids exist, graph is acyclic, tool names are in the registry, arg schemas type-check. Scheduler (no LLM): maintain the ready frontier (nodes whose deps are all complete); dispatch all ready nodes concurrently up to a concurrency limit; on completion substitute outputs into dependents' placeholders and update the frontier. Optionally stream: begin executing nodes as soon as they are parsed. After the DAG completes, a joiner/solver LLM either produces the final answer or emits a new DAG given the collected evidence (dynamic replanning), bounded by max_replans.
  - When to use: Tool- and retrieval-heavy tasks with multiple independent lookups (query many requirement IDs, test-log shards, parts, standards clauses); cost- or latency-sensitive paths; when observations are not needed to decide the plan's shape.
  - Trade-offs: Latency 1.8-3.7x lower and cost 3.4-6.7x lower than ReAct at equal or better accuracy (LLMCompiler); tokens ~5x lower on HotpotQA (ReWOO). Planner never sees observations, so plans can be wrong when the task shape depends on intermediate results; requires replanning and robust parsing (HuggingGPT planning F1 ~50%, format instability). Degrades gracefully on tool failure (ReWOO -29 vs ReAct -41).
  - Literature defaults: Temperature 0 for planning; JSON or line-based plan grammar with constrained decoding or a logit bias toward structural tokens (HuggingGPT used +0.2 on braces) plus a repair/retry pass; concurrency limit = tool rate limits (typically 4-16); max_replans = 2-3; per-node timeout and retry (1 retry) before marking failed and replanning; each node receives only its own inputs and a short task description (ReWOO) rather than the full history.
  - Sources: An LLM Compiler for Parallel Function Calling; ReWOO: Decoupling Reasoning from Observations for Efficient Augmented Language Models; HuggingGPT: Solving AI Tasks with ChatGPT and its Friends in Hugging Face; Planning Agents (Plan-and-Execute, ReWOO, LLMCompiler in LangGraph)

- **As-needed recursive decomposition with AND/OR plans (ADaPT, with TDAG re-decomposition)** - controller(task, depth): if depth > d_max return FAIL. result = executor(task) where the executor is an interleaved agent (ReAct-style) with a step cap that must end with an explicit completed/failed verdict, ideally confirmed by an external check. If success return. Else plan = planner(task, executor_trace) producing 3-5 sub-tasks combined with AND (all must succeed, in order) and OR (alternatives tried in order until one succeeds). Evaluate the logical expression by calling controller(sub, depth+1) for each operand; short-circuit OR on first success and AND on first failure. TDAG extension: after each AND operand completes, re-call the planner on the remaining sub-tasks conditioned on results so the rest of the plan adapts; optionally instantiate a per-sub-task executor configuration (tool subset, retrieved skills).
  - When to use: Interactive or environment-dependent tasks where the right granularity is unknown in advance (debugging, incident triage, multi-file code changes, data pipelines); heterogeneous task difficulty where always decomposing would waste cost on easy cases.
  - Trade-offs: Large gains over both ReAct and static Plan-and-Execute (ALFWorld 71.6 vs 43.3/43.3; TextCraft 52 vs 19/27) and far fewer cascading failures (TDAG 4.35% vs 34.78%). Costs extra calls on hard cases and relies on the executor's self-reported failure (which Huang et al. show is unreliable without external signals); worst case is exponential in d_max without caps.
  - Literature defaults: d_max = 3 (4 for deeply compositional domains); 3-5 sub-tasks per plan; executor step cap 10-20 actions; adapt d_max to executor strength (weaker executors benefit from deeper decomposition: 3.3% -> 41.7%); re-plan remaining sub-tasks after each completed sub-task (TDAG); temperature 0.
  - Sources: ADaPT: As-Needed Decomposition and Planning with Language Models; TDAG: A Multi-Agent Framework based on Dynamic Task Decomposition and Agent Generation; ReAct: Synergizing Reasoning and Acting in Language Models

- **Search over thoughts: BFS/DFS tree search and MCTS over sub-goal states (ToT / GoT / RAP)** - Represent partial solutions as states; a proposer LLM generates k candidate next thoughts per state (sampling i.i.d. or proposing a list); an evaluator LLM scores states either independently (value: sure/likely/impossible, sampled v times and averaged) or comparatively (vote among candidates, sampled v times). BFS keeps the top-b states per level up to depth T; DFS explores with pruning when value is 'impossible' and backtracks. GoT generalization: allow Aggregate nodes that merge several states (divide-and-conquer with merge), Refine self-loops, and KeepBest(h). RAP variant: run MCTS with UCT where the LLM proposes actions and predicts next states; reward = weighted sum of action log-likelihood, state-confidence (modal share across samples), self-evaluation P(Yes), and task heuristic (e.g., constraints satisfied); run N iterations and return the highest-reward path (optionally aggregate answers across iterations).
  - When to use: Tasks with verifiable or scoreable intermediate states and combinatorial choice (scheduling, assembly ordering, constraint satisfaction, design-space exploration, test-sequence planning); merge-heavy tasks over large inputs (sorting/deduplicating requirement lists, merging overlapping documents).
  - Trade-offs: Large accuracy gains where applicable (Game of 24 4% -> 74%; Blocksworld 4-step 0.02 -> 0.88; GoT sorting error -62% vs ToT) at 5-10x the tokens of a single CoT call (ToT $0.74 vs CoT-SC $0.47 per Game of 24 case); LLM ranking reliability is unproven in general (planning survey) and gains shrink on small instances (GoT at 32 elements negligible). Needs a hard step/iteration cap.
  - Literature defaults: ToT: BFS breadth b=5, value sampling v=3 per state, depth T = number of required steps (3 for Game of 24), DFS cap 100 steps / 10 intermediate steps; for generation tasks depth 2, 5 candidates, 5 votes. GoT sorting template: split 2, generate 5 keep 3, merge 10 keep 1, refine 10 keep 1. RAP: 10-20 MCTS iterations (RAP(20) > RAP(10)), UCT exploration, reward mixing confidence + task heuristic; aggregate answers across iterations for QA (+3 points).
  - Sources: Tree of Thoughts: Deliberate Problem Solving with Large Language Models; Graph of Thoughts: Solving Elaborate Problems with Large Language Models; Reasoning with Language Model is Planning with World Model (RAP)

- **Reflection-driven replanning with external feedback and bounded episodic memory (Reflexion / Self-Refine, gated by Huang et al.)** - Loop for trial t = 1..T_max: run the plan/executor; obtain feedback f_t from an EXTERNAL source (tool error, failing unit tests, schema/constraint violation, verifier output, retrieval contradiction, human review). If f_t indicates success, stop. Else call a reflector LLM with (task, trajectory, f_t) to write a short structured reflection: root cause, what to do differently, which sub-goal to change. Append to a memory buffer capped at Omega entries (FIFO). Re-plan with the task + memory. Self-Refine variant for quality (not correctness): generate -> critique against an explicit rubric -> revise, 2-3 rounds. Never trigger replanning from a bare self-judgment of correctness.
  - When to use: Any sub-goal with a real success signal: code (tests), structured outputs (schema), plans (precondition/dependency verifier), retrieval (citation check), configuration (dry-run). Quality refinement when rubric criteria are explicit (completeness vs checklist, style).
  - Trade-offs: With real feedback: +22% absolute on AlfWorld within 12 trials, HumanEval 80 -> 91, 82% of failed Blocksworld plans fixed in ~3.7 verifier rounds. Without external feedback accuracy falls (GPT-4 GSM8K 95.5 -> 89.0); self-generated tests can have high false-positive rates (MBPP 16.3%) and reverse gains. Each trial multiplies cost; loops can settle in local minima.
  - Literature defaults: T_max = 3 trials (Reflexion stops HotPotQA after 3 consecutive failures; most verifier fixes land by round 3-4; cap 5 for verifier backprompting); memory cap Omega = 1-3 reflections; up to 6 generated unit tests for code with a note that self-generated tests must be treated as weak signals; Self-Refine 2-3 rounds with explicit rubric; temperature 0 for the reflector.
  - Sources: Reflexion: Language Agents with Verbal Reinforcement Learning; Self-Refine: Iterative Refinement with Self-Feedback; Large Language Models Cannot Self-Correct Reasoning Yet; On the Planning Abilities of Large Language Models: A Critical Investigation

- **Multi-plan generation and selection by self-consistency voting** - Sample k candidate plans (or k sub-goal answers) at temperature T with the same prompt; normalize the outputs (e.g., canonical sub-goal list or final answer string); select by majority vote, or for plans by scoring each candidate with a lightweight checker (acyclic, all tools valid, covers all task requirements) and picking the modal valid plan. Use the agreement ratio (votes for winner / k) as a confidence score to route: high agreement -> execute; low agreement -> escalate to search or human.
  - When to use: Final answers to closed-form sub-goals; selecting among candidate decompositions when no verifier exists; as a confidence estimator for routing and for deciding whether to decompose further.
  - Trade-offs: k-fold token cost (parallelizable, so little added latency); large gains on reasoning (GSM8K +17.9) that saturate quickly; outperforms multi-agent debate at equal budget (88.2 vs 83.0 at 9 samples); only applies where answers can be canonicalized and offers no guarantee for open-ended text.
  - Literature defaults: k = 5 for plan selection and routine sub-goals, 10-20 for high-stakes answers, 40 as the published upper reference; T = 0.7 (top-k 40) for sampling; agreement threshold ~0.6 for 'confident'; run samples in parallel via the parallelization component.
  - Sources: Self-Consistency Improves Chain of Thought Reasoning in Language Models; Large Language Models Cannot Self-Correct Reasoning Yet; Understanding the planning of LLM agents: A survey

- **Interleaved reasoning-acting executor with loop and premature-stop guards (ReAct hardened)** - For each sub-goal, run a loop of Thought -> Action(tool, args) -> Observation appended to context until a Finish action or step cap. Guards: (1) validate action names/args against the registry before dispatch (AgentBench Invalid Action); (2) detect repeated identical or semantically equivalent actions (hash of tool+args) and inject a 'you already tried this; change approach or finish' message, or escalate to replanning (LLMCompiler observed ~10% looping runs); (3) require a completion checklist before Finish to prevent early stopping (~85% premature stops observed on Movie Rec); (4) on reaching the cap, fall back to a pure reasoning answer with self-consistency (ReAct -> CoT-SC gave the best HotpotQA EM, 35.1).
  - When to use: Sub-goals whose next step depends on observations (navigating a codebase, interactive debugging, exploratory data queries, web/UI tasks); as the leaf executor inside ADaPT-style recursion.
  - Trade-offs: Grounding nearly eliminates hallucination (0% vs 56% for CoT) but raises reasoning errors (47% vs 16%) and is slow and token-heavy because the full history is resent every step; prone to loops and early stopping, which are the dominant agent failures (Task Limit Exceeded).
  - Literature defaults: Step cap 10-20 per sub-goal (ReAct used ~7 for HotpotQA and up to ~30-50 for ALFWorld-style environments); repeated-action threshold 2; one fallback to CoT-SC with k=5 on cap; temperature 0; truncate observations to a fixed token budget per step.
  - Sources: ReAct: Synergizing Reasoning and Acting in Language Models; An LLM Compiler for Parallel Function Calling; AgentBench: Evaluating LLMs as Agents

- **Program-aided execution: plan as executable code with interpreter-backed computation (PAL / PoT / Code-Then-Execute)** - The planner emits each sub-goal (or the whole plan) as a program in a restricted language (Python subset) where natural-language reasoning appears as comments or variable names and every computational step is code: arithmetic, unit conversion, table joins, date math, regex extraction over logs, calls into registered tools exposed as functions. The program is statically checked (allowed imports, allowed tool functions, no network/filesystem), executed in a sandbox with CPU/memory/time limits, and its return value becomes the sub-goal result. Exceptions are captured as structured feedback and fed to a bounded repair loop (re-prompt with traceback). Programs are stored with their inputs as cache keys and as regression tests.
  - When to use: Any sub-goal whose correctness depends on exact computation or data manipulation (numeric claims from test logs, BOM roll-ups, tolerance stack-ups, schedule arithmetic); tasks over structured/tabular data; when the plan must be auditable and replayable.
  - Trade-offs: Large accuracy gains on computation-heavy tasks (GSM8K Codex PAL 72.0 vs CoT 65.6; GSM-Hard 61.2 vs 23.1; PoT ~+12 avg) with no extra model calls, but requires a hardened sandbox, adds failure modes (syntax/runtime errors, wrong API usage) that need a repair loop, and is weaker for open-ended language sub-goals. Code generation quality depends on the model's coding ability more than on its reasoning ability.
  - Literature defaults: Temperature 0 for code; one automatic repair attempt on exception with the traceback appended, then fall back to a language-only executor; sandbox timeout 10-30 s per program, no network by default; tool functions exposed with typed signatures and docstrings; majority-vote over k=5-40 program outputs only for high-stakes numeric answers (PAL reaches 80.4% on GSM8K with 40 samples).
  - Sources: PAL: Program-aided Language Models; Program of Thoughts Prompting: Disentangling Computation from Reasoning for Numerical Reasoning Tasks; Design Patterns for Securing LLM Agents against Prompt Injections; Defeating Prompt Injections by Design (CaMeL)

- **Reasoning-guided interleaved retrieval (IRCoT)** - Initialize with a retrieval using the task text (top-k paragraphs). Loop: (1) generate exactly one more reasoning sentence conditioned on the task, all retrieved paragraphs so far, and the reasoning so far; (2) if the sentence contains a final answer marker, stop; otherwise use that sentence as the next retrieval query, retrieve k paragraphs, add them (deduplicated) to the evidence set. Terminate on answer, step cap, or evidence budget. Optionally finish with a separate reader call over the full collected evidence (the paper reports this is often better than reading the CoT's own answer).
  - When to use: Multi-hop lookups where later queries depend on earlier findings (trace a requirement to its tests to its failures; follow references across standards clauses); when up-front DAG planning cannot know the sub-questions.
  - Trade-offs: Up to +21 retrieval recall and +15 QA points over one-shot retrieval on HotpotQA/2Wiki/MuSiQue/IIRC and reduced hallucination; works with small models (Flan-T5-large) without training. Costs one LLM call plus one retrieval per step with a growing context, so it is slower and more expensive than static planning and cannot parallelize across hops.
  - Literature defaults: k = 4-8 paragraphs per step (paper tuned k in {2,4,6,8}); cap steps at 6-8 and total evidence at the model's safe context (paper capped around 15 paragraphs); temperature 0; distinct reader call for the final answer; use the same retriever and chunking as the pipeline RAG component so evidence can be cached across sub-goals.
  - Sources: Interleaving Retrieval with Chain-of-Thought Reasoning for Knowledge-Intensive Multi-Step Questions (IRCoT); Measuring and Narrowing the Compositionality Gap in Language Models (Self-Ask)

- **External formal planner with LLM translation (LLM+P) inside an LLM-Modulo generate-test-critique loop** - Maintain a human-authored domain model (PDDL domain or an equivalent constraint/scheduling model: operators with preconditions and effects, resources, constraints). The LLM's job per task: (1) translate the natural-language task into a problem instance (objects, initial state, goal) in the formal language, using one in-context example of a correctly formalized problem; (2) a parser validates syntax and that all symbols exist in the domain; (3) a solver (Fast Downward, OR-Tools, Z3) returns a plan or UNSAT; (4) a verifier (VAL-style) checks the plan against the model; (5) the LLM translates the plan back to natural language or to tool calls. If the solver returns UNSAT or the parser fails, return the structured error to the LLM for a bounded re-formalization. LLM-Modulo generalizes this: when no complete domain model exists, the LLM proposes plans and a bank of critics (hard constraint checkers, simulators, style/preference critics, humans) returns structured critiques that are appended to the next proposal prompt.
  - When to use: Formalizable domains with real constraints and optimality needs: test-campaign scheduling, assembly sequencing, resource allocation, change rollout ordering, configuration selection. Use the critic-bank variant when the domain is only partially formalizable.
  - Trade-offs: Delivers sound and often optimal plans where raw LLM planning gives ~34% validity (Blocksworld) or ~14% (Logistics), but requires a maintained domain model and a formalization step that is itself error-prone (the LLM+P authors report the quality of the PDDL context is decisive). Re-formalization loops add latency; solvers can time out on large instances and need horizons/limits.
  - Literature defaults: One in-context formalized example per domain (LLM+P); temperature 0 for formalization; max 3 re-formalization rounds on parse/UNSAT errors; backprompting with verifier feedback capped at 5 rounds (Valmeekam et al.: 82% of a 50-instance Blocksworld set solved in avg 3.68 rounds); solver time limit 10-60 s; when the solver fails, degrade to the LLM plan plus verifier flags rather than silently proceeding.
  - Sources: LLM+P: Empowering Large Language Models with Optimal Planning Proficiency; LLMs Can't Plan, But Can Help Planning in LLM-Modulo Frameworks; On the Planning Abilities of Large Language Models: A Critical Investigation

- **Trajectory-level Monte Carlo tree search with reflection and environment reward (LATS)** - State = (task, trajectory of thought/action/observation steps). Selection: UCT over children. Expansion: sample n candidate next actions (ReAct-style) from the LM. Evaluation: value = weighted sum of an LM-estimated score (prompted to rate progress 1-10) and, when the trajectory is terminal, the environment's reward (tests passed, task success, score). Simulation: roll out to a terminal state or depth cap. Backpropagation: update values along the path. On a failed terminal node, generate a Reflexion-style verbal reflection and attach it to the context used when expanding siblings/ancestors. Return the best-valued successful trajectory or the best-scoring one at budget exhaustion.
  - When to use: High-value sub-goals where the environment gives a usable reward (code with tests, API tasks with checkable end state, web/UI tasks with scores) and single-trajectory ReAct is unreliable; not for cheap or latency-critical tasks.
  - Trade-offs: Reports 92.7% pass@1 on HumanEval (GPT-4) and 75.9 WebShop score (GPT-3.5), ahead of ReAct/Reflexion/ToT, but costs many full trajectories per task (n children x depth x iterations) and adds wall-clock latency; the LM value estimates are noisy, so gains depend on real environment rewards being available for terminal nodes.
  - Literature defaults: n = 5 children per expansion, depth cap equal to the ReAct step cap (7-15), 20-30 iterations max (paper used small budgets, e.g., n=5 and up to ~30 iterations), UCT exploration weight ~1.0, value = 0.5*LM score + 0.5*environment reward on terminals, one reflection per failed terminal added to sibling expansions, stop immediately on the first trajectory with full environment reward.
  - Sources: Language Agent Tree Search Unifies Reasoning, Acting, and Planning in Language Models (LATS); Tree of Thoughts: Deliberate Problem Solving with Large Language Models; Reflexion: Language Agents with Verbal Reinforcement Learning

- **Skeleton-then-parallel-expansion with a strategy router (Skeleton-of-Thought / SoT-R)** - A router (a prompted LLM or a small fine-tuned classifier) decides whether the task's answer is decomposable into independent sections. If yes: call the model to produce a short numbered skeleton (3-10 points, each a few words); then issue one parallel call per point ('expand point i in 1-2 paragraphs, given the full skeleton'); concatenate in order and optionally run a light merge/dedupe pass. If no (math derivations, code, narrative writing, tightly dependent reasoning): fall back to normal sequential generation or to a dependency-aware plan.
  - When to use: Report and document generation sub-goals (status summaries, multi-section analyses, FMEA sections, compliance mappings) where sections are independent; latency-sensitive user-facing paths.
  - Trade-offs: Up to 2.39x end-to-end speedup across 12 models with quality at least as good in ~60% of cases; degrades coherence/immersion and hurts math, coding, writing and Fermi-style questions, hence the router. Costs more total tokens (skeleton repeated in each expansion) in exchange for latency.
  - Literature defaults: Skeleton of 3-10 points, each <= 5 words; expansions capped at 1-2 paragraphs; router threshold tuned so math/code/narrative route to sequential; a 100M-class classifier (paper: RoBERTa fine-tuned on LIMA annotations) matched or beat a GPT-4 prompt router; run expansions through the parallelization component with the same concurrency limits as tool fan-out.
  - Sources: Skeleton-of-Thought: Prompting LLMs for Efficient Parallel Generation; How we built our multi-agent research system

- **Control-flow integrity for decomposition: Plan-Then-Execute, Dual LLM and capability-tagged evidence (prompt-injection hardening)** - Partition the system into a privileged planner that sees only trusted inputs (user task, domain profile, tool catalog) and quarantined executors that touch untrusted data (retrieved documents, tool outputs, web pages). The planner commits the action list/DAG before any untrusted data is read (Plan-Then-Execute). Every evidence variable (#E_k / $k) carries provenance tags (source, trust level, readers). The scheduler enforces policies at dispatch: tagged-untrusted values may not select which tool runs, may not be used as recipients/targets/paths of write or destructive actions without human approval, and may not expand the plan. Replanning after execution is allowed only through a constrained joiner that receives summarized, schema-validated results (not raw text) and whose output is again policy-checked. Untrusted documents are processed by isolated map workers with no tools whose outputs are reduced by a separate step (LLM Map-Reduce). Evaluate with an injection benchmark (AgentDojo-style) measuring both utility and injected-action rate.
  - When to use: Always, for any deployment where sub-goals read data the organization does not fully control (supplier documents, tickets, emails, web search, logs containing user-supplied text) and where some tools write to systems of record or execute commands.
  - Trade-offs: CaMeL retains 77% task success vs 84% undefended on AgentDojo with provable policy enforcement; Plan-Then-Execute reduces adaptivity (the dossier's dynamic replanning must be constrained), and policies add engineering and occasional false blocks. Does not defend against injections in the user's own prompt.
  - Literature defaults: Default-deny policy for writes/destructive actions whose arguments derive from untrusted-tagged values; summarize tool outputs to a fixed schema and token cap before they reach any planner/joiner; max_replans 1-2 when untrusted data has entered the context; isolated map workers with no tool access and a per-chunk output schema; log provenance of every argument of every tool call; release gate: injected-action rate 0% on the internal injection suite at acceptable utility loss (budget ~5-10 points).
  - Sources: Design Patterns for Securing LLM Agents against Prompt Injections; Defeating Prompt Injections by Design (CaMeL); AgentDojo: A Dynamic Environment to Evaluate Prompt Injection Attacks and Defenses for LLM Agents; ReWOO: Decoupling Reasoning from Observations for Efficient Augmented Language Models

- **Effort-scaling and sub-task specification protocol for orchestrator-worker decomposition** - Embed explicit scaling rules in the orchestrator prompt that map task complexity to a budget: number of sub-agents/sub-tasks, tool calls per sub-task, and total tokens (e.g., simple fact: 1 worker, 3-10 tool calls; comparison: 2-4 workers, 10-15 calls each; complex: 10+ workers). Each delegated sub-task is a structured spec: objective, expected output schema, allowed tools and preferred sources, explicit boundaries (what not to do, what others cover), and stop criteria. The orchestrator writes its plan to persistent memory before delegation so it survives context truncation, runs workers in parallel, synthesizes, and decides on another round only if coverage gaps are explicit. Evaluate by end state and by an LLM judge with a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency), plus human review of edge cases.
  - When to use: Breadth-first information-gathering and analysis tasks that parallelize (survey many documents, requirements or log shards); not for tightly coupled sequential work such as most code edits, where single-agent or fixed pipelines are better.
  - Trade-offs: Anthropic reports +90.2% over single-agent on an internal research eval and up to 90% lower wall-clock time, but ~15x the tokens of a chat interaction; token spend explains ~80% of performance variance, so budgets directly trade quality for cost. Early versions over-spawned workers and duplicated searches until scaling rules and task specs were added.
  - Literature defaults: Scaling rules as above; 3-5 parallel workers per round; each worker 3+ parallel tool calls where independent; plan persisted to memory at ~200k-token context ceilings; a dedicated citation/attribution pass after synthesis; small eval set (~20 realistic queries) early, LLM-judge rubric scored 0-1 per criterion, pass^k over repeated runs for reliability; rainbow deployment for prompt/planner updates.
  - Sources: How we built our multi-agent research system; Building effective agents; Claude prompting best practices (chain complex prompts, subagent orchestration, parallel tool calling)

- **Verified executable skill library with embedding retrieval (Voyager-style procedural memory)** - When a sub-task succeeds, package its solution as a skill: an executable program or parameterized plan fragment, a natural-language description generated by the model, input/output schema, the verification that passed, and provenance. Embed the description and store it in a vector index. On a new task, retrieve top-k skills by similarity to the task/sub-task description and insert them into the planner's context as callable handlers (or as exemplars). Skills are only admitted after an external check (tests pass, verifier accepts, end-state diff correct), are versioned, and are periodically re-validated against the current tool registry; failed reuse decrements a reliability score that gates retrieval.
  - When to use: Recurring sub-tasks across many tasks in a domain (standard extraction routines, common queries over test-log stores, recurring compliance checks); long-lived deployments where planning cost should amortize.
  - Trade-offs: Compounds capability and cuts planning cost (Voyager: 3.3x more items, 15.3x faster milestones vs. prior Minecraft agents; TDAG's skill library contributed to its ItineraryBench gains), but introduces stale/incorrect skills if admission is not externally verified and can bias the planner toward retrieved but suboptimal methods; index and schema maintenance is ongoing work.
  - Literature defaults: Top-k = 5 retrieved skills (Voyager); admission requires an external verification pass; store description embeddings from a cheap model; reliability score with decay, drop below threshold (e.g., <0.7 success over last 10 uses) removes a skill from retrieval; re-validate skills whenever a referenced tool's schema version changes.
  - Sources: Voyager: An Open-Ended Embodied Agent with Large Language Models; TDAG: A Multi-Agent Framework based on Dynamic Task Decomposition and Agent Generation; Decomposed Prompting: A Modular Approach for Solving Complex Tasks

- **Fixed hierarchical pipeline decomposition as the default baseline (Agentless pattern)** - For a known task family, hand-design a coarse-to-fine pipeline instead of an autonomous planner: (1) hierarchical localization narrows the search space in stages (e.g., repository -> files -> classes/functions -> edit hunks; or test campaign -> suite -> failing cases -> log windows), each stage a bounded LLM call over a compact structured view (tree/outline) plus retrieval; (2) candidate generation produces N alternative outputs (patches, root-cause hypotheses) with sampling; (3) validation filters candidates with external checks (reproduce the failure, run regression tests, schema/constraint checks) and selects by majority among passing candidates. No step lets the LLM choose the next action.
  - When to use: Whenever the task family is known and stable (bug fixing, root-cause triage, requirement-to-test mapping); as the mandatory baseline before adopting recursive/autonomous decomposition for a domain.
  - Trade-offs: On SWE-bench Lite Agentless reached 32.0% at $0.70/issue, the best open-source result at the time, beating agent frameworks that cost several times more; predictable cost and easy debugging, but no adaptivity to unforeseen task shapes and requires per-domain engineering.
  - Literature defaults: 3 localization levels; N = 4-10 candidate outputs at temperature ~0.8; validation by reproduction test plus existing regression tests; selection by majority vote among candidates that pass all tests, with a fallback to the top-ranked candidate flagged for human review; per-issue cost budget enforced at the pipeline level.
  - Sources: Agentless: Demystifying LLM-based Software Engineering Agents; Building effective agents

## Architecture recommendations

- 1. Expose one interface, many strategies. Define a Decomposer component with a single entry point decompose(task_prompt, context, config) -> Plan, where Plan is a typed DAG (nodes: id, kind in {llm, tool, retriever, recursive, verify, aggregate}, args with $ref placeholders, deps, success_criteria, budget). Implement strategies as plugins behind this interface: direct (no decomposition), plan-and-solve (zero-shot plan), least-to-most (sequential carry-forward), dag-planner (LLMCompiler/ReWOO style), adaptive-recursive (ADaPT/TDAG), search (ToT/GoT/RAP), and orchestrator-workers (Anthropic). A strategy selector picks per task using cheap signals: estimated step depth, presence of tools, independence of sub-goals, verifiability of intermediate states, and latency/cost SLOs.
- 2. Separate Planner, Scheduler, Executor, Verifier, Replanner as distinct modules with explicit state (plan, past_steps, evidence, reflections), following the LangGraph plan-and-execute / LLMCompiler decomposition. The Scheduler is pure code (no LLM): topological frontier scheduling with a concurrency limit, per-node timeout/retry, placeholder substitution and streaming start. The Replanner (joiner) is an LLM call bounded by max_replans (default 2-3).
- 3. Make plans machine-validated before execution. Use a strict JSON schema (HuggingGPT-style id/dep/args) with constrained decoding or a logit bias toward structural tokens, then run static checks: acyclicity, referenced ids exist, tool names and argument types match the registry, every task requirement maps to at least one node (coverage), and no node exceeds a per-step computation-depth bound (Faith and Fate). Invalid plans go to a repair prompt (one attempt) and then to a fallback strategy. Planning F1 for GPT-3.5 was only ~50% in HuggingGPT's evaluation; validation, not trust, is the design stance.
- 4. Decompose lazily by default and recursively on failure. Try the whole task with a bounded executor first; on externally confirmed failure, plan 3-5 sub-tasks with AND/OR composition and recurse to d_max=3 (ADaPT). After each completed sub-task, re-plan the remainder conditioned on results (TDAG) to prevent cascading failures. Gate decomposition on estimated depth (Least-to-Most gains appear at 5+ steps) so easy tasks cost one call.
- 5. Treat the LLM planner as a proposer and put correctness in verifiers. Every node declares success_criteria that an external check can evaluate: schema validation, unit tests, constraint/precondition checkers, retrieval grounding checks, numeric recomputation by tools, or a symbolic solver for formalizable domains (LLM-Modulo). Reflection/replanning is triggered only by these signals, never by the model re-reading its own output (Huang et al.). Backprompt with the verifier's error message for at most 3-5 rounds.
- 6. Use a registry of sub-task handlers (Decomposed Prompting) addressed by name with docstring-quality descriptions, examples, edge cases and poka-yoke parameter design (Anthropic ACI guidance). Handlers include LLM prompts (with per-handler exemplar sets), symbolic tools, retrievers, and the planner itself (recursion). Retrieve the top-k relevant handlers into the planner prompt when the catalog is large to respect context limits.
- 7. Route models by role: strongest available model for planning, verification synthesis and the joiner; smaller/cheaper models for leaf execution and extraction (ReWOO's 7B planner result and LangChain's cost guidance). Log every blueprint/plan with its outcome to build a distillation set for a small domain-specific planner.
- 8. Hard budgets everywhere: per-node step cap (10-20), per-plan node cap (e.g., 25), recursion depth cap (3-4), replan cap (2-3), reflection memory cap (1-3), wall-clock and token budgets with graceful degradation to a direct CoT-SC answer. Implement loop detection (repeated tool+args hash) and a completion checklist before Finish, since Task Limit Exceeded, Invalid Format and Invalid Action dominate agent failures (AgentBench, LLMCompiler).
- 9. Make parallelism a first-class plan property: the planner prompt instructs that independent sub-goals have no deps and dependent ones reference placeholders; the scheduler runs the frontier concurrently; self-consistency samples and candidate-plan voting are fanned out through the same parallel executor. Include a damping rule so trivial tasks are not decomposed or delegated (Anthropic subagent guidance).
- 10. Configuration surface for any domain: a DomainProfile object containing (a) planner exemplars and the PS+-style 'extract relevant variables' instruction tailored to the domain (e.g., part numbers, tolerances, requirement IDs, timestamps), (b) the handler/tool subset, (c) verifiers and success criteria, (d) decomposition heuristics (depth gate, base-case sizes, chunking rules), (e) budgets and SLOs, (f) output schema. Strategies read only from the profile, so swapping domains never touches code.
- 11. Observability and evaluation hooks at every chain boundary: persist plan, node inputs/outputs, verifier verdicts, reflections, timing and tokens; compute step-wise metrics (plan validity rate, sub-goal success rate, compositionality gap, replans per task) alongside end-to-end success, as the planning survey notes that final-success-only evaluation hides decomposition failures.
- 12. Human checkpoints and safety: expose an approval hook on nodes tagged irreversible or high-impact (writes to systems of record, destructive commands), default-on for engineering operations; run agents in sandboxes; keep plans human-readable so reviewers can approve or edit a plan before execution (visible planning steps per Anthropic).
- Security as a plan property (missing entirely from the dossier): implement Plan-Then-Execute control-flow integrity and provenance tags on evidence variables. The privileged planner sees only trusted inputs; untrusted tool/document outputs are schema-summarized before any planner or joiner sees them; policies at dispatch block writes, deletes, sends and command execution whose arguments derive from untrusted-tagged data unless a human approves. Add an AgentDojo-style injection suite to CI and gate releases on injected-action rate (target 0%) at an accepted utility cost.
- Adopt a failure taxonomy richer than AgentBench's execution-level classes: label every failed trace with MAST's 14 modes (task-spec disobedience, step repetition, loss of history, failure to ask for clarification, task derailment, information withholding, premature termination, no/incomplete/incorrect verification, etc.). Several map to concrete controls: an explicit termination criterion per sub-task, a 'clarification' sub-goal type when specs are ambiguous, and verification by a node other than the producer.
- Score plans, not just answers: use TaskBench-style node-F1 / edge-F1 / parameter-F1 against reference tool graphs for the planner module, PlanBench task families (including obfuscated domains) to detect pattern-matching planners, and report reliability as pass^k over repeated runs (tau-bench) alongside pass@1. Evaluate stateful tasks by end-state diff rather than trajectory match. Keep a small (~20) realistic query set from day one and grow it from production failures.
- Cost control through explicit effort scaling: encode complexity-to-budget rules in the planner prompt (workers, tool calls per worker, token ceiling), because token usage explains most of the performance variance and multi-agent decomposition costs ~15x a chat turn. Enforce per-task token and dollar budgets in the scheduler with graceful degradation (fewer workers, smaller k, direct answer) and surface cost per solved task as a first-class metric.
- Re-benchmark explicit decomposition per model generation. Reasoning models (o1, DeepSeek-R1, current Claude with adaptive thinking) internalize much of plan-and-solve, ToT-style search and self-consistency; the component should expose a 'thinking effort' knob as a strategy and reserve explicit DAG decomposition for what internal reasoning cannot deliver: parallel tool execution, inspectable intermediate state, verifier hooks, cost isolation and security boundaries. Treat the dossier's accuracy deltas (mostly measured on GPT-3.5/GPT-4/PaLM-era models) as hypotheses to re-test, not constants.
- Default to a fixed hierarchical pipeline (Agentless pattern) for known task families and require autonomous/recursive decomposition to beat it on cost and reliability before adoption. Fixed pipelines are easier to observe, cache, secure and regression-test; the Agentless SWE-bench Lite result shows they can also win on accuracy per dollar.
- Make computation a code sub-goal: add a sandboxed program executor handler (PAL/PoT) so numeric, tabular and date/log arithmetic never happens in natural language. Statically restrict imports and tool bindings, cap CPU/time, capture exceptions as structured feedback for one bounded repair attempt, and store programs as cache keys and regression tests.
- Observability: emit one trace per task with spans per plan node (inputs, outputs, provenance tags, verifier verdicts, tokens, latency, model/version, retries), persist plans outside the context window so they survive truncation, and log the planner's effort-scaling decision. Use rainbow (overlapping-version) deployments so in-flight long-running plans are not broken by planner or prompt updates, and version prompts, handler schemas and skills so any trace can be replayed.
- Treat the recursive AND/OR planner as an HTN: maintain an explicit method library (task -> subtask network with preconditions) so the planner selects among known decompositions before inventing new ones, and keep acyclicity, bounded fan-out and recursion depth as termination guarantees (unrestricted recursive HTN planning is semi-decidable), not just cost knobs. Admit new methods/skills to the library only after external verification and track their reliability.
- Feasibility-weighted sub-goal selection: attach a cheap feasibility predicate to every handler (tool reachable, inputs present, permissions, data available, rate-limit headroom) and multiply it into the planner's choice among candidate steps (SayCan), and map each emitted step to the nearest admissible registry action before dispatch (Huang et al. 2022). Track executability and correctness separately, since forcing executability can silently lower correctness.
- Where retrieval shape is unknown, run IRCoT-style interleaved retrieval as the leaf executor (one reasoning sentence -> one retrieval per hop, fixed k and hop cap) instead of forcing a static DAG; where it is known, keep ReWOO/LLMCompiler static plans for parallelism. Make the strategy selector's decision ('does the answer shape depend on what is found?') an explicit logged field so it can be learned from outcomes.

## Documented pitfalls

- Cascading failure from frozen up-front plans: an early sub-goal error propagates through the whole plan (planning survey: decomposition-first con; TDAG measured 34.78% of Plan-and-Execute errors as cascading vs 4.35% with dynamic re-decomposition). Mitigate with re-planning after each sub-goal, OR-alternatives, and verifier gates between nodes.
- Static Plan-and-Execute can be worse than no planning on interactive tasks (ADaPT: WebShop 17.0 vs ReAct 32.0). Mitigate by lazy/as-needed decomposition and keeping an interleaved executor as the leaf.
- Intrinsic self-correction degrades accuracy (Huang et al.: GPT-4 GSM8K 95.5 -> 89.0 after two rounds; GPT-3.5 CommonSenseQA 75.8 -> 38.1); reported Reflexion/RCI gains relied on oracle labels. Mitigate by triggering reflection only from external feedback and otherwise spending budget on self-consistency.
- Unreliable self-reported success and self-generated tests: Reflexion's MBPP Python result fell (80.1 -> 77.1) with a 16.3% test false-positive rate; ADaPT's executor failure signal is a self-heuristic. Mitigate with independent verifiers (real test suites, schema checks) and treat self-judgment as a weak prior.
- Looping and premature stopping in interleaved agents: ~10% of LLaMA-2 ReAct HotpotQA runs looped past 4 calls and ~85% of GPT-3.5 Movie Rec runs stopped early (LLMCompiler); Task Limit Exceeded is the dominant AgentBench failure. Mitigate with repeated-action detection, completion checklists, step caps and a reasoning fallback.
- Format and action invalidity: AgentBench reports Invalid Format (~14%) and Invalid Action (~10%) as major failure classes; HuggingGPT cites output-format instability and planning F1 ~50%. Mitigate with JSON schemas, constrained decoding/logit bias, validation against the tool registry, and a bounded repair pass.
- Compositionality gap that does not shrink with scale (~40%, Self-Ask): sub-goals correct but composition wrong. Mitigate by always re-asking the original question with sub-answers in context (Least-to-Most), adding an explicit composition/aggregation node, and tracking the gap as a metric.
- Depth-driven decay (Faith and Fate): accuracy falls with computation-graph depth because models pattern-match subgraphs. Mitigate by bounding per-step depth and delegating exact computation to tools.
- Autonomous plan infeasibility: GPT-4 produced valid Blocksworld plans only ~34% of the time and collapsed to 2-9% on obfuscated domains (Valmeekam et al.); the planning survey lists hallucinated entities/tools and precondition violations. Mitigate with external verifiers/backprompting (82% of failures fixed in ~3.7 rounds) or symbolic planners seeded by LLM plans.
- Reasoning-error shift in grounded agents: ReAct cut hallucination to 0% but raised reasoning errors to 47% (vs 16% for CoT) and 23% search-result errors. Mitigate by combining modes (ReAct -> CoT-SC) and improving retrieval quality.
- Cost blow-up of search and voting: ToT uses ~5x the completion tokens of CoT and CoT-SC k=100 is costly; GoT's advantage vanishes on small instances. Mitigate by gating search on task size/verifiability and keeping b, k and depth as configured budgets.
- Over-decomposition and over-delegation: frontier models may spawn subagents or chain steps where a direct call suffices (Anthropic docs); extra reasoning overhead and context-length pressure cause plan forgetting on long trajectories (planning survey). Mitigate with a depth gate, damping instructions, and compact per-node context (ReWOO).
- Context-length limits on tool catalogs (HuggingGPT): too many tool descriptions crowd the planner prompt. Mitigate by retrieving relevant handlers per task.
- Semantic misunderstanding is not fixed by planning (Plan-and-Solve: 27% of errors unchanged). Mitigate with retrieval grounding, variable-extraction instructions, and clarification sub-goals.
- Benchmark/evaluation blind spot: most benchmarks score only final success (planning survey), hiding plan-quality regressions. Mitigate with step-wise metrics and plan-validity tests.

## Evaluation metrics

- End-to-end task success rate / exact match / F1 on multi-step benchmarks (GSM8K, HotpotQA, 2WikiMultiHopQA, MuSiQue, Bamboogle, DROP, ALFWorld, WebShop, TextCraft, AgentBench, ItineraryBench, Game of 24, Blocksworld/PlanBench) and on in-house engineering task suites
- Compositionality gap: fraction of tasks where all sub-goals are correct but the composed answer is wrong (Self-Ask)
- Plan validity rate: share of emitted plans passing schema, acyclicity, tool-existence, argument-type and coverage checks before any repair; repair success rate
- Plan quality vs reference: precision/recall/F1 of predicted sub-tasks and edit distance of task order (HuggingGPT planning evaluation), plus GPT-4/LLM-judge score for graph plans
- Sub-goal success rate and per-depth success curve (ADaPT analysis by d_max and problem depth); average decomposition depth actually used
- Cascading-failure rate: fraction of failures attributable to an upstream sub-goal error (TDAG)
- Failure-class distribution: Task Limit Exceeded, Invalid Format, Invalid Action, Context Limit Exceeded (AgentBench), plus loop-detection and premature-stop counts (LLMCompiler)
- Efficiency: LLM calls per task, total tokens per task (ReWOO reports tokens; LLMCompiler reports cost multiples), wall-clock latency and speedup vs a sequential baseline, DAG parallelism ratio (critical path length / total nodes)
- Cost per solved task in dollars and tokens (ToT reports cost per case), and accuracy-per-dollar Pareto curves across strategies
- Verifier-loop metrics: fraction of failed plans repaired, average backprompt rounds to success (Valmeekam: 3.3-3.7), reflection trials to success (Reflexion), false-positive rate of success signals (Reflexion MBPP 16.3%)
- Self-consistency agreement ratio distribution and calibration (agreement vs accuracy) used for routing
- Robustness under tool failure (accuracy drop with tools returning no evidence, ReWOO) and under distribution shift in task length/complexity (SCAN length split, list-length generalization)
- Human preference / pairwise win rate for open-ended outputs (ToT creative writing protocol) and rubric-based LLM-judge scores for Self-Refine loops
- Operational: planner-call share of total cost, cache hit rate on sub-goals/plans, human-checkpoint invocation rate, time-to-first-executed-node when streaming plans

## Engineering adaptation notes

- Code tasks: use orchestrator-workers / ADaPT recursion for multi-file changes (Anthropic names this the canonical case for dynamic decomposition); leaf executors are ReAct loops over repo tools; success criteria are compilers, linters and real test suites, not self-generated tests (Reflexion HumanEval 80 -> 91 with tests, MBPP down with weak tests); cap reflection trials at 3.
- Specifications, requirements and standards documents: apply GoT-style split -> per-chunk extraction -> aggregate/merge DAGs for coverage and conflict detection (document-merging and keyword-counting templates); use Self-Ask-style sub-questions with a retriever attached per hop for clause lookups; include a 'variable extraction' step (PS+) for requirement IDs, units, tolerances and normative verbs (shall/should).
- Test logs and incident reports: decomposition-first DAG planning shines because sub-queries (per shard, per service, per time window) are independent and parallelizable (LLMCompiler 1.8-3.7x latency gains); add symbolic handlers (regex, SQL, statistics) to keep per-step computation depth low (Faith and Fate), and a verifier node that recomputes any numeric claim with a tool.
- CAD/BOM metadata: treat structural checks (part-of hierarchy, quantity roll-ups, mass/cost sums, interface compatibility) as symbolic verifier handlers; the LLM planner proposes the plan and a solver or rules engine owns correctness (LLM-Modulo, Valmeekam et al.); use MCTS/RAP-style search only for ordering/configuration problems where a heuristic reward (constraints satisfied) exists.
- Planning and scheduling tasks (test campaigns, assembly sequences, change rollouts): seed a symbolic planner/scheduler with the LLM plan (LPG search steps 15.8 -> 8.9 with GPT-4 seeds) and backprompt with verifier errors for up to 5 rounds.
- Domain profiles: encode domain exemplars for the decomposer (the biggest lever in few-shot decomposition), a tool/handler subset, success criteria per node type, chunking/base-case sizes (e.g., one requirement section, one log window), and output schemas; the same engine then serves safety analyses, FMEA drafting, root-cause analysis, compliance mapping, etc.
- Human-in-the-loop placement: engineering outputs often feed systems of record (requirements databases, PLM, ticketing); tag nodes that write or recommend irreversible actions for approval and surface the plan for review before execution, which also provides the external feedback the reflection loop needs.
- Model selection: pick planner models using agentic benchmarks (AgentBench shows a large gap between frontier API models and <=70B open models); if open-source executors are required, add stronger validation, loop detection and smaller step caps; distill domain planners from logged blueprints (ReWOO 7B planner parity).

## Composition notes

- Hybrid retrieval: decomposition produces retrieval-sized sub-questions; attaching retrieval per sub-question (Self-Ask + Search: 2WikiMultiHopQA 30.0 -> 40.1; Decomposed Prompting's symbolic retrieval handler) outperforms retrieving on the original query. Retrieval also feeds the planner with relevant tool/handler descriptions and past plans, and retrieval hits are a grounding signal the verifier can use to reject hallucinated sub-goals.
- Answer verification: verification is the external feedback that makes reflection/replanning work (Reflexion, LLM-Modulo backprompting) and is unsafe to omit (Huang et al.). Compose as verify nodes in the DAG after each sub-goal and after the final aggregation; use the compositionality gap and plan-validity checks as verification targets; share self-consistency sampling between the two components (agreement ratio as confidence).
- Parallelization: the plan DAG is the parallelization component's input; the scheduler runs the ready frontier concurrently (LLMCompiler 3.7x latency / 6.7x cost), fans out self-consistency and candidate-plan samples (voting), runs ToT/GoT candidates per level in parallel, and executes TDAG sub-agents concurrently when independent. The planner prompt must mark independence explicitly; the parallel component enforces concurrency limits and rate limits.
- Caching: cache (a) plans/blueprints keyed by normalized task + domain profile (ReWOO blueprints are observation-free and therefore highly reusable), (b) sub-goal results keyed by handler + canonical args (deterministic DAG nodes are natural cache keys), (c) successful sub-task solutions as skills retrieved by similarity (TDAG incremental skill library), and (d) verifier outcomes. Lazy decomposition plus caching means repeated tasks skip planning entirely; stream cache hits into the frontier so dependents start immediately.
- Pipeline RAG: decomposition is the control plane of a pipeline RAG system: it decides which sub-questions need retrieval, which need generation, which need tools, and how results merge (GoT aggregate nodes). The retrieve -> generate -> verify chain per sub-question is itself a prompt chain; the final synthesis node is the ReWOO Solver / LLMCompiler joiner. Multi-hop RAG benchmarks (HotpotQA, MuSiQue, 2Wiki) are the shared evaluation surface.
- Prompting and architecture best practices: follow the simplest-structure-first ladder (direct call -> prompt chaining -> routing -> parallel sectioning/voting -> orchestrator-workers -> evaluator-optimizer -> agent) from Anthropic; keep reasoning before answers (CoT), make plans visible and separately logged (chain boundaries), write handler/tool descriptions like docstrings with poka-yoke parameters, add damping rules against over-delegation, and enforce iteration caps and human checkpoints. Decomposition then becomes the shared skeleton onto which the other five components attach at node boundaries.
